# Changelog

Все значимые изменения в проекте GigaAM v3 Transcriber будут документированы в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/),
и этот проект придерживается [семантического версионирования](https://semver.org/lang/ru/).

## [Unreleased]

## [2.5.3-3] - 2026-09-24

### Исправлено

- **Liquid: список файлов.** Счётчик выбранных файлов выровнен с кнопкой
  «Очистить»; в строках появился крестик для удаления отдельного файла
  без очистки остальных.

## [2.5.3-2] - 2026-09-24

### Изменено

- **Liquid: отдельный headless-компаньон.** Нативное приложение теперь
  встраивает `GigaAMWorker.app` без PyQt; классическая `GigaAMTranscriber.app`
  по-прежнему выпускается отдельно. Обработка, Live, LLM и загрузка медиа
  используют прежний Python-протокол; офлайн-вариант включает модели.

### Исправлено

- **Согласованные версии Liquid и worker.** Оба macOS-бандла получают версию
  `2.5.3-2`; CI сверяет номера версий в online- и offline-архивах и
  останавливает публикацию при несовпадении.

## [2.5.2] - 2026-09-23

### Исправлено

- **Liquid: папка результатов из «Изменить» больше не сбрасывается.** Если
  поле пути было в фокусе, выбранная папка показывалась в поле, но в
  настройках оставался пустой путь, и результаты сохранялись рядом с исходным
  файлом. При перестройке страницы старое поле при удалении из окна
  записывало своё пустое значение поверх выбранной папки. PyQt не затронут.

### Изменено

- **Абзацы в TXT.** Обычный `.txt` больше не одна сплошная строка: абзац
  закрывается только на конце предложения — после паузы от 2 с или когда
  абзац длиннее ~700 символов. Текст без пунктуации (CTC/RNNT) делится на
  стыках сегментов. В `_diarize.txt` внутри блока `[Спикер]` те же абзацы
  вместо строки на каждый сегмент, рвущей фразы посередине. Таймкоды,
  Markdown и субтитры не изменились.

## [2.5.1] - 2026-09-23

### Исправлено

- **Локальный MCP в установке TUI:** добавлена зависимость `yt-dlp`, без
  которой `gigaam mcp` завершался при импорте загрузчика медиа. Установщик
  проверяет MCP entry point через `--help`, не загружая модель.
- **ASR по требованию в локальном MCP:** подключение harness больше не
  загружает веса; каждый `transcribe` загружает отдельную модель и освобождает
  её после обработки. Статус и каталог моделей остаются доступны без весов;
  HTTP/REST/веб сохраняют постоянную модель.
- При выгрузке ссылка загрузчика на веса освобождается до очистки кэша
  backend, чтобы буферный пул MLX не удерживал уже ненужную модель.
- **Подпись macOS-приложения:** статистика обработки по умолчанию сохраняется
  в пользовательском каталоге конфигурации, а не рядом с исполняемым файлом
  внутри `.app`. Распознавание больше не изменяет подписанный bundle.

### Документация

- Добавлен [гайд локальной интеграции harness](LOCAL_HARNESSES.md):
  Claude Code, Codex, OMP, Pi, OpenCode и Hermes; настройка venv через uv,
  скиллы, таймауты, проверка реальной транскрибации и безопасный rollback.

## [2.5.0] - 2026-09-22

### Добавлено

- **TUI 2.0.** Терминальный клиент переработан:
  - интерфейс по-русски по умолчанию, `/lang ru|en` / `--lang` переключает
    язык и хранит его в общей с настольным приложением настройке `language`;
    все статусы, подсказки, справка и описания команд двуязычны
    (`tui/src/i18n.rs`), тест-«ловушка» запрещает английские литералы в
    статусах и журнале; headless-вывод для агентов остаётся английским;
  - вкладки Обработка / LLM / Настройки / Журнал (F1–F4, Tab/Shift+Tab,
    клик), панель параметров рядом с очередью, строка «Далее:» с подсказкой
    следующего шага, справка по `?` со всеми клавишами и командами;
  - вкладка «Настройки» вместо меню `/settings`: список строк, Enter или
    клик меняет значение; LLM-страница с транскриптами, режимами,
    провайдером и прокручиваемым ответом (при нескольких режимах — все
    ответы с заголовками);
  - мышь: вкладки, кнопки, строки очереди и настроек, колёсико; `/mouse off`
    возвращает выделение текста терминалу;
  - цветовые темы: `/theme` (меню без аргумента, имя с аргументом, Tab
    дописывает имя), строка «Тема» в настройках, `--theme NAME` на один
    запуск, выбор хранится в `tui_settings.json`; 102 схемы — `default`,
    `mono`, `dark-hermes-pink` и 99 палитр oh-my-pi (MIT,
    `tui/themes/LICENSE-oh-my-pi`);
  - обновление до ratatui 0.30 / crossterm 0.29 / ratatui-image 11.
- **REST API по образцу OpenAI Audio API.** `POST /v1/audio/transcriptions`
  (multipart `file` + `model` с алиасами `whisper-1` и др.; форматы json /
  text / srt / vtt / verbose_json / diarized_json; `stream=true` — SSE с
  `transcript.text.delta` / `transcript.text.done`), расширения GigaAM
  (`diarize`, `diarization_backend`, `num_speakers`, `asr_backend`,
  `onnx_provider`, `audio_preprocessing`), `GET /v1/models[/{id}]`,
  авторизация `Authorization: Bearer` (`X-API-Key` принимается), ошибки в
  конверте OpenAI, 429 с `Retry-After`. Работает с официальными SDK через
  `base_url=".../v1"`. Справочник — `docs/API.md`, Postman-коллекция обновлена.
- **MCP-сервер для ИИ-агентов** (`src/services/mcp_server.py`,
  `src/services/mcp_backend.py`, `src/mcp_server.py`; SDK `mcp>=2,<3`).
  Инструменты `transcribe` (источник `url` / `path` / `audio_base64`,
  форматы `text|json|verbose|diarized|srt|vtt`, диаризация, прогресс через
  MCP progress notifications), `summarize` (`summary|tasks|terms|custom`
  через настроенный LLM-провайдер), `list_models`, `list_llm_providers`,
  `server_status`; ресурсы `gigaam://models`, `gigaam://status`; промпты
  `meeting_notes`, `subtitles_review`. Ошибки — `[code] message` с кодами
  REST-контракта. Транспорты: stdio (`gigaam mcp` в лаунчере TUI,
  `python -m src.mcp_server`) и Streamable HTTP `/mcp` в `api.py` и
  веб-панели (ключ `Authorization: Bearer` из общего `.api_keys`; без ключа
  — 401 в конверте OpenAI). Один путь транскрибации для REST и MCP:
  `api.py` вызывает `mcp_backend.run_transcription`. В HTTP-режиме `path`
  запрещён, пока не задан `GIGAAM_MCP_ALLOW_PATHS=1` (с ограничением
  `GIGAAM_MCP_PATH_ROOT`); лимит base64 — `GIGAAM_MCP_MAX_INLINE_MB`.
  Хранилище ключей вынесено в `src/services/api_keys.py`, настройки LLM для
  Python-слоя — `src/services/llm_settings.py`. Скиллы для агентов:
  `skills/gigaam` получил раздел MCP, новый `skills/gigaam-mcp` описывает
  контракт для агентов без локальной установки; `gigaam --install-skill`
  и установщик ставят оба. Документация — `docs/MCP.md`, фрагмент nginx —
  `deploy/nginx-mcp-location.conf`, тест `tests/test_docs_mcp.py` следит,
  чтобы каждый инструмент был описан.

### Изменено (breaking)

- Старое REST API удалено: `/api/v1/transcribe[/batch]`, `/api/v1/tasks*`,
  `/api/v1/download-batch`, `/api/v1/asr/options`, очередь задач и хранение
  результатов на диске. Ответ возвращается синхронно. Примеры в настольных
  приложениях и документации переведены на новый API; старые руководства по
  API и Postman заменены `docs/API.md`.
- `TASK_CLEANUP_HOURS` и `RATE_LIMIT_API` больше не читаются;
  `RATE_LIMIT_UPLOAD` действительно ограничивает частоту запросов, а
  неразборное значение останавливает сервер при старте.

### Исправлено

- **Воркер TUI завершался сразу после старта («Worker exited»).** Стартовая
  проверка CLI-провайдеров (`<tool> --version`) передавала детям stdin
  воркера, и `pi --version` выставлял на нём O_NONBLOCK — воркер принимал
  EAGAIN за EOF и выходил; пробы и LLM-запуски получают `DEVNULL`, а
  собственный stdin воркер читает устойчиво к смене флагов.
- Первый Esc во время обработки посылает воркеру мягкую отмену, как обещает
  подсказка.
- API проверяет загрузку до чтения тела: без заголовка авторизации или с
  `Content-Length` больше лимита ответ приходит сразу, файл не сохраняется.

## [2.3.1] - 2026-09-21

### Исправлено

- **Сборка офлайн-моделей повторяет загрузку с HuggingFace.** В CI 2.3.0
  Intel-сборка упала на одной неудачной попытке скачать silero VAD
  (транзиентная ошибка HF на shared-раннере, `LocalEntryNotFoundError`);
  `scripts/build_offline_models.py` теперь делает до четырёх попыток с паузами
  10/30/60 с для ASR, VAD и обеих моделей диаризации.
- **Кэш torch, скачанный сборкой на другом Python, больше не считается
  установленным.** `~/Library/Caches/GigaAMGUICash/torch/<variant>` общий для
  всех сборок приложения; `is_installed()` сравнивал только версии пакетов.
  PyQt-сборка на Python 3.12 клала туда cp312-колёса, а CI-компаньон Liquid на
  3.11 активировал их и падал на `import torch` («Failed to load PyTorch C
  extensions»: 3.11 не видит `_C.cpython-312-darwin.so` и берёт папку-заглушку
  `_C/`). Теперь рантайм считается установленным только с расширением под
  текущий интерпретатор, а чужой ABI получает свою папку `<variant>-cp311`;
  сборка со встроенным torch продолжает им пользоваться.

## [2.3.0] - 2026-09-21

### Добавлено

- **TUI: реестр LLM-провайдеров из воркера** (`llm_tools`/`llm_tool_check`).
  `/settings` показывает выбранного провайдера с версией установленного CLI
  вместо статичного списка имён; новые команды `/llm-path` (путь к бинарю),
  `/llm-provider-name` (внутренний provider для Pi/oh-my-pi), `/llm-args`
  (дополнительные аргументы CLI), `/llm-tools on|off` (разрешить агенту
  инструменты и сохранение сессии). Провайдер «Other» теперь действительно
  запускается.
- **TUI: стриминг ответа LLM.** Текст выводится по мере поступления
  `llm_chunk`, результат остаётся на экране после завершения — хоткей `r`
  показывает и скрывает его повторно. `Esc` во время работы LLM отправляет
  воркеру `llm_cancel` и останавливает только LLM-запрос, не перезапуская
  воркер целиком (как это делает `Esc` во время транскрибации).
- **`/llm-file <путь>`** — добавляет в очередь LLM любой `.txt`/`.md`/`.srt`/
  `.vtt`-транскрипт, а не только файлы, полученные в текущей сессии.
- **`/audio-mode auto|off|light|denoise`** — выбор режима предобработки звука
  прямо в TUI, как у десктопного приложения; активный режим виден в шапке.
- **TUI: общие настройки с десктопным приложением.** Если
  `user_settings.json` основной программы существует, TUI считается, что она
  установлена, и общие ключи (backend/модель, форматы, диаризация,
  количество спикеров, настройки LLM) читаются и пишутся туда же, а
  `LLM_API_KEY` — в `.env` рядом (ключ никогда не хранится в
  `tui_settings.json`). Без установленной десктопной программы всё, включая
  ключ, остаётся в `tui_settings.json`, и `.env` не создаётся. Выигрывает
  последний, кто сохранил: другая программа подхватывает изменения при
  следующем запуске, не раньше.
- **Headless-режим: `gigaam transcribe` и `gigaam llm`** — те же воркер и
  сохранённые настройки, что у интерактивного TUI, но без экрана: одна
  строка на файл на stdout (`✓ name.wav → /path/name.txt`), прогресс и логи
  на stderr (`--quiet` — тихо), `--json` — построчный поток событий воркера
  на stdout, при этом stderr *воркера* подавлен (собственные сообщения
  `gigaam` — «worker unavailable», неверные аргументы — по-прежнему идут в
  stderr). Коды выхода: `0` — всё успешно, `1` — хотя бы один файл с
  ошибкой, `2` — неверные аргументы или несуществующий входной файл
  (сообщение в stderr, на stdout ничего даже с `--json`), `3` — воркер
  не запустился (см. `gigaam --update`).
- **`gigaam --update [--ref REF]`** обновляет TUI, окружение воркера и
  прописывает `~/.local/bin` в PATH (`conf.d` fish, `.zshrc`, `.bashrc`);
  `gigaam --version` печатает установленную ревизию; `gigaam --install-skill`
  (пере)устанавливает агентский skill в `~/.claude/skills`, `~/.codex/skills`,
  `~/.agents/skills` — только в те каталоги, которые уже существуют.
- **`skills/gigaam/SKILL.md`** — контракт для агентов: точные команды
  `gigaam transcribe`/`gigaam llm`, формат `--json`-потока, коды выхода, куда
  сохраняются результаты, что делать при коде `3`, и что интерактивный TUI
  без терминала запускать нельзя.
- **`scripts/install_tui.sh`** при обновлении сохраняет выбранную модель и не
  пересоздаёт `.venv`/`tui/target` (`--fresh` — полная переустановка с нуля);
  регистрирует `~/.local/bin` в PATH через `conf.d` fish, `.zshrc` и
  `.bashrc` (`--no-path` — не трогать rc-файлы); ставит
  `requirements-macos-mlx.txt` на Apple Silicon, чтобы синхронизированный из
  десктопного приложения backend `mlx` действительно работал в TUI
  (`--no-mlx` — пропустить); устанавливает `skills/gigaam/SKILL.md`
  (`--no-skill` — пропустить).

### Исправлено

- **CHANGELOG 2.2.0 обещал, что TUI спрашивает у воркера `llm_tools`** — до
  этой ветки TUI получал ответ, но никак его не использовал и всегда слал
  заглушечные имена бинарей в `llm_start`. Теперь это действительно так:
  `/settings` и меню провайдера показывают версию установленного CLI, а
  запуск LLM использует найденный воркером путь к бинарю.
- **Тесты TUI писали в реальный `tui_settings.json` разработчика.** Тесты,
  идущие через `run_command`, теперь используют `isolated_config_dir()` —
  `GIGAAM_CONFIG_DIR`, указывающий на временный каталог теста.
- **Битый `user_settings.json` десктопного приложения больше не обнуляет его
  API-ключ.** TUI читал `LLM_API_KEY` из `.env` только после успешного
  парсинга `user_settings.json` и при первом же сохранении писал в `.env`
  пустую строку, стирая ключ. Обе стороны используют один и тот же признак
  «десктопное приложение установлено» (файл существует), ключ читается из
  `.env` независимо от того, распарсился ли JSON, а пустое значение в `.env`
  никогда не пишется.
- **`gigaam --update` больше не сбрасывал выбранную модель и не пересобирал
  `.venv`/Rust-таргет на каждом обновлении** (см. выше, `install_tui.sh`).
- **PyQt: главная панель вкладок отцентрована** — раньше `QTabBar` прижимал
  шесть вкладок влево, оставляя пустую полосу справа при минимальной ширине
  окна.

## [2.2.1] - 2026-09-19

### Исправлено

- **Второе приложение при транскрибации в GigaAM Liquid.** Замороженный
  companion при каждом файле запускал ещё один «GigaAM Transcriber», который
  прыгал в Dock и падал. Причина — `multiprocessing.resource_tracker`
  перезапускал `app.py` без `--native-worker`, а `freeze_support()` никто не
  вызывал. Вызов добавлен первым действием `app.py`; в PyQt-сборках баг
  маскировался instance-lock'ом.
- **Liquid: папка результатов.** Пустое поле больше не подменяется на
  `~/Documents/GigaAM` — результаты сохраняются рядом с исходным файлом, как в
  PyQt. Заданная вручную папка сохраняется как раньше.
- **Liquid: кнопка «Журнал обработки»** больше не сдвигается при смене
  процентов прогресса.

### Изменено

- **Понятный журнал обработки во всех интерфейсах.** Строки формируются
  по-русски у источника (processor, model_loader, ASR-бэкенды, конвертер,
  worker): вместо `DEBUG: …`, `ASR сегментация: VAD, окон декодера`, `MLX
  backend load requested`, `КРИТИЧЕСКАЯ ОШИБКА` и кодов FFmpeg — «Подготавливаем
  звук…», «Речь найдена: участков — 3», «Говорящих найдено: 2», «Готово за 21
  сек». Причины очистки звука переведены. Deprecation-предупреждения
  библиотек больше не попадают в журнал.
- **Английский интерфейс переводит журнал целиком** — одной таблицей
  `src/core/log_i18n.py` для PyQt и Liquid (Swift-копия генерируется
  скриптом и проверяется тестом), включая строки с именами файлов, числами
  и длительностями.

### Добавлено

- **Liquid: drag & drop папок.** Перетащенная или выбранная папка сканируется
  рекурсивно по тем же расширениям, что и в PyQt.
- `swift test` для UI-независимой логики Liquid (`GigaAMLiquidCore`) в CI.

## [2.2.0] - 2026-09-18

### Добавлено

- **oh-my-pi** (`omp`) как LLM-провайдер во всех интерфейсах (PyQt, Liquid,
  web, TUI): печатный режим `omp -p --mode text`, внутренний provider, модель
  и доп. аргументы — как у Pi.
- **Реестр LLM-провайдеров** `src/services/cli_tools.py` — единственный
  источник правды о провайдерах, бинарях и способе их поиска. Список больше не
  захардкожен в шести местах: PyQt читает реестр, web — `GET /api/llm/tools`,
  Liquid и TUI спрашивают воркер (`llm_tools`, `llm_tool_check`).
- **Автопоиск CLI-инструментов.** Кроме `PATH` процесса проверяются типичные
  каталоги установки: `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`,

## [1.5.4] - 2026-09-06

### Исправлено

- **Linux: перецепка на монитор падала на локализованной системе.** `pactl`
  переводит вывод: в `ru_RU` заголовок записи — `Выход источника №101`, а
  sample-spec — `s32le 2-канальный 4800`. Обе регулярки парсера написаны под
  C-локаль, поэтому `source_outputs()` всегда возвращал пустое множество, своя
  запись не находилась, `attach_to_monitor()` вырабатывал двухсекундный таймаут
  и старт системного захвата падал с `Could not move the capture stream to
  monitor source ...` — в `system.flac` оставалось около двух секунд входа по
  умолчанию. Частота монитора при этом читалась как 4800 вместо 48000 и
  спасалась только запасным значением. Теперь локаль задаём мы: `pactl`
  вызывается с `LC_ALL=C` (issue #49). Обход `LC_ALL=C` для всего приложения
  больше не нужен.
- **`mix.flac` растягивался в разы и терял микрофон.** Микшер брал позицию
  каждого чанка из метки его прихода и делал длину блока равной
  «сдвиг + длина». Сдвиг между источниками знака не имеет: даже дрожание
  меток в ±90 мс добавляло `abs(сдвиг)` тишины в **каждую** пару. На сессии
  98,6 с из 5 300 пар это дало файл 480,6 с (×4,87), в котором речь тонула
  между растущими промежутками тишины, — при идеальных `mic.flac` и
  `system.flac` (issue #50). Проявлялось только при живом системном источнике,
  то есть после фикса #49. Теперь позиция чанка на дорожке микса берётся из
  смещения сэмплов, а не из часов, и микшер ведёт непрерывную выходную
  дорожку: аудио, чей парный источник ещё не догнал, придерживается до его
  прихода, а не набивается тишиной. Формат дорожки фиксируется первым блоком,
  так что замолчавший на секунду микрофон больше не может перевести микс на
  48 кГц и стоить его целиком.

## [1.5.0] - 2026-09-01

### Исправлено

- Буферный пул MLX больше не растёт бесконтрольно. `unload()` искал
  `clear_cache` в пакете `mlx`, хотя функция живёт в `mlx.core`, — промах молча
  глушился `except`, и пул не возвращался системе ни на одном пути. На записи в
  117 минут пул доходил до 37.91 ГБ при реальной пиковой потребности 1.65 ГБ.
  На Apple Silicon это общая память, поэтому съедалась именно оперативка, и в
  RSS процесса рост виден не был.
- Модель диаризации NeMo Sortformer больше не остаётся в памяти навсегда.
  `SortformerDiarizationManager` хранит её в словаре уровня класса, но не
  переопределял `unload()` — унаследованный чистил только ссылку экземпляра.
  Затрагивало все платформы: на CUDA это ~1.5 ГБ удержанной VRAM на карте
  фиксированного объёма.
- Аудио для pyannote загружается как float32. По умолчанию soundfile отдаёт
  float64, и обе копии жили одновременно: 0.837 ГБ плюс 0.418 ГБ на записи в
  117 минут.
- GUI освобождает кэши ускорителя после пачки файлов. Раньше это делали все
  остальные интерфейсы (web, api, cli), но не GUI, а его `ModelLoader`
  создаётся один раз при старте и живёт всю сессию.
- Кнопка «Очистить» снова забывает запомненную папку, когда очередь уже пуста.
  Фикс 1.4.4 добавил сброс папки, но спрятал его за условием «очередь
  непустая». После перезапуска очередь пуста, поэтому кнопка выходила на первой
  строке, и папка подставлялась при каждом старте без возможности её сбросить.
  То же исправлено для списка транскриптов LLM.

### Изменено

- На Apple Silicon VAD по умолчанию считается на ускорителе (`ASR_VAD_DEVICE`
  теперь `auto`, а не `cpu`). На записи в 117 минут VAD занимал 598 секунд на
  CPU против 18 на MPS при идентичном результате. На CUDA дефолт остаётся
  `cpu`: там у ускорителя отдельный ограниченный бюджет VRAM. Переменная
  окружения `ASR_VAD_DEVICE` по-прежнему всё переопределяет, а при сбое VAD
  остаётся штатный откат на разбиение с перекрытием.

### Производительность

- Полный цикл на записи в 117 минут: потребление системной памяти снижено с
  37.1 ГБ до 4.9 ГБ, время ASR+VAD — с 598 до 73 секунд, диаризации — с 33 до
  16 секунд. Результат распознавания идентичен: те же 428 сегментов ASR и 1608
  сегментов диаризации.
- Убран повторный прогон ffmpeg: `processor` уже готовит 16 кГц моно WAV, а
  MLX-бэкенд декодировал этот же файл ещё раз. Для нестандартных форматов
  сохранён откат на ffmpeg.

  backend `pyannote`; при ошибках ONNX/Sortformer журнал не уводит пользователя
  к нерелевантной причине.

- Built-binary smoke `--sortformer-onnx-smoke` теперь проверяет не только ONNX

## [1.3.1] - 2026-07-20

### Исправлено

- Issue #32: native Windows больше не пытается импортировать неподдерживаемый
  NVIDIA NeMo при выборе Sortformer. Backend всегда маршрутизируется в
  независимую реализацию Streaming Sortformer v2.1 через ONNX Runtime.
- Загрузка моделей больше не начинается от одного выбора пункта в интерфейсе.
  После нажатия «Начать обработку» приложение сначала готовит всю выбранную
  цепочку и только затем переходит к первому файлу.
- Недостающие ASR-веса, DeepFilterNet, Pyannote, ONNX-диаризация и Sortformer
  теперь обнаруживаются до обработки. Ошибка загрузки относится к конкретному
  компоненту и не маскируется успешным стартом очереди.
- Папка моделей из offline-архива больше не используется как каталог записи.
  Она остаётся read-only, а модели, отсутствующие в комплекте, сохраняются в
  пользовательский Hugging Face-кэш приложения.
- Проверка локальных PyTorch-весов учитывает выбранную модель GigaAM, включая
  CTC/RNNT-варианты и соответствующий tokenizer, а не только `v3_e2e_rnnt`.
- При явно заданном числе спикеров ONNX-диаризация объединяет несколько
  локальных дорожек одного окна максимумом вероятностей. Прежнее усреднение
  могло опускать реальную речь ниже onset-порога и терять фрагменты реплик.
- Windows/Linux portable теперь содержат один `onnxruntime-gpu` вместо
  конфликтующих CPU/GPU-дистрибутивов. CPU provider остаётся внутри GPU-wheel.
- ONNX `auto` на Windows/Linux однозначно выбирает CUDA → CPU. DirectML больше
  не перехватывает `auto`, но остаётся доступен как явная advanced-настройка.
- Перед обнаружением CUDA provider приложение активирует уже выбранный
  `cu124`/`cu128` runtime и вызывает `onnxruntime.preload_dlls()`, поэтому ONNX
  использует те же CUDA/cuDNN, что и PyTorch ASR.
- Native NeMo Sortformer на Apple Silicon теперь использует MPS. При ошибке
  transfer/inference выполняется ровно один повтор на CPU, причина показывается
  в журнале, фиктивная односпикерная разметка не создаётся.

### Добавлено

- Portable Sortformer ONNX без зависимости от PyTorch/NeMo: закреплены
  репозиторий `Scrybl/diar_streaming_sortformer_4spk-v2.1`, точная ревизия и
  SHA-256 модели; перед inference проверяются checksum и имена входов/выходов.
- Общий контракт подготовки компонентов со стадиями `checking`, `downloading`,
  `loading`, `ready`, `failed` и `cancelled`.
- Двуязычный журнал GUI для подготовки моделей. Для DeepFilterNet дополнительно
  показываются объём и процент скачивания с шагом 10%.
- Реальный CI smoke для Windows portable: собранный `.exe` скачивает Sortformer
  ONNX, открывает CPU-сессию ONNX Runtime и выполняет один streaming inference.
- Реальный CoreML smoke на macOS portable и CPU-fallback smoke на Windows/Linux;
  отчёт содержит requested provider и providers созданной ORT-сессии.
- В обработочный журнал добавлены provider chain для ONNX, device для NeMo и
  явное сообщение о fallback MPS → CPU.
- MIT-лицензия `parakeet-rs`, алгоритм которого использован как референс для
  streaming state и постобработки portable Sortformer.

### Как теперь работает подготовка

1. Выбор backend или модели в GUI ничего не скачивает.
2. После «Начать обработку» строится план только для выбранной конфигурации:
   ASR; DeepFilterNet для режимов `auto`/`denoise`; диаризация, если она включена.
3. Для каждого компонента проверяются bundled cache и пользовательский cache.
   Найденные веса сразу загружаются; отсутствующие сначала скачиваются.
4. Все компоненты готовятся один раз до первого файла и переиспользуются всей
   очередью. При ошибке очередь не стартует, а журнал показывает проблемный этап.
5. Отмена до или между этапами завершает подготовку без запуска обработки.

Поведение Sortformer зависит от платформы и типа сборки:

- **Windows portable:** NeMo не ищется и не устанавливается. Используется
  Sortformer ONNX; публичная модель скачивается при первом запуске обработки.
  В сборке находится `onnxruntime-gpu`, а `auto` выбирает CUDA → CPU. CUDA/cuDNN
  берутся из выбранного приложением runtime `cu124`/`cu128`.
- **macOS full `.app`:** пакет NeMo уже встроен в приложение. При первом запуске
  скачиваются только официальные веса NVIDIA Sortformer; `HF_TOKEN` не нужен.
  NeMo работает через MPS с диагностируемым CPU fallback.
- **Linux portable:** как и Windows, содержит `onnxruntime-gpu` с цепочкой
  CUDA → CPU. При установленном NeMo используется официальный backend; без него
  автоматически выбирается Sortformer ONNX.
- **macOS ONNX:** `auto` использует CoreML → CPU. Это относится к ONNX ASR,
  ONNX-диаризации и portable Sortformer.
- **Pyannote:** при первом запуске проверяются все необходимые gated-модели.
  Нужны действующий `HF_TOKEN` и принятые условия каждой модели.
- **Offline-архив:** содержит базовую ONNX-цепочку ASR, VAD и кластерную
  Pyannote+WeSpeaker-диаризацию. Sortformer намеренно не включён из-за размера;
  при его выборе веса докачиваются в пользовательский кэш, если сеть доступна.
